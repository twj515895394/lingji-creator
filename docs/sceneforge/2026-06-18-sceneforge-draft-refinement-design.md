# SceneForge Draft Refinement — 详细设计

> 日期：2026-06-18  
> 状态：已定稿  
> PRD：`.scratch/sceneforge-draft-refinement/PRD.md`

## 1. 目标

为 SceneForge 增加一个清晰的中间态能力：用户不满意当前草案时，不必只能“整版盲重跑”或“先提交后修订”，而是可以提供一次性补充意见，让系统基于当前草案重新生成一版新的整阶段草案。

## 2. 范围

- 所有支持草案生成的阶段
- 一次性临时补充意见
- 整阶段草案优化
- 阶段固定落盘策略
- Studio 动作边界与验收口径

不包含分字段编辑、分段编辑或长期备注。

## 3. 核心行为

- 用户在当前阶段已有草案时，可触发“补充优化”。
- 系统将当前草案、阶段上下文和用户一次性补充意见组合后，重新生成一版新的整阶段草案。
- 这次补充意见不会写入项目长期状态，也不会自动成为下次生成的默认提示。
- 若该阶段定义为“必须人工提交”，则新草案仍停留在待审阅区，用户确认后再落盘。
- 若该阶段定义为“可自动落盘”，则生成成功后可直接进入现有落盘与后续校验/审批链。

## 4. 设计约束

- refinement 是独立动作，不与普通 run / regenerate / request revision 混成同一按钮语义。
- 是否必须人工提交是阶段定义固定配置，不开放项目级或运行时覆盖。
- 不引入第二条写盘路径；自动落盘阶段也必须通过现有受控写盘出口。
- UI 必须让用户清楚知道：这次输入的是“一次性补充意见”，不是长期备注。

## 5. 建议的能力拆分

### 5.1 Runner / Service

- 新增 refinement 输入模式或等价输入结构
- 可读取当前待提交草案作为 refinement 基础
- 可把一次性补充意见传给 runner

### 5.2 阶段策略

- 在阶段定义真相源中声明：
  - `manual_submit_required`
  - `auto_commit_if_generated`

### 5.3 Studio

- 当阶段支持草案生成且已有可优化草案时，显示“补充优化”入口
- 提供简洁的一次性输入区
- 生成后根据阶段策略走不同后续路径

## 6. 风险

- 若把“补充优化”和“重新生成”做成同一动作，用户会不清楚当前草案是否会被参考。
- 若把补充意见持久化，会污染项目长期状态并让后续运行行为变得不可预测。
- 若把自动落盘做成运行时开关，会让产品语义复杂化并提升测试矩阵。
