# SceneForge 选题闸门创作意图检查设计

> 日期：2026-07-02
> 状态：已确认，待进入实施计划
> 关联阶段：`SceneForge / topic_gate`
> 关联现状：
> - `docs/project-stage-summary/2026-07-02-sceneforge-remix-stage-summary.md`
> - `docs/sceneforge/2026-06-19-sceneforge-topic-gate-llm-analysis-design.md`

## 1. 问题背景

当前 `topic_gate` 的“创作意图”入口只有单行输入框，且默认假设用户已经知道该写什么。这对熟悉流程的用户问题不大，但对新手有两个明显缺口：

1. 输入经常过薄，只写一句模糊话题，缺少足以决定整段视频方向的关键信息。
2. 用户没有在早期被强制补齐方向信息，后续 `设计图 / 分镜 / 视频提示词` 虽然能继续跑，但很容易整体跑偏，最后产物不是用户真正想要的。

这说明 `topic_gate` 现在缺少一个前置闸门：它不仅要能“保存简报”和“分析选题”，还要先判断“这段创作意图是否足以支撑后续整条生成链路”。

## 2. 目标

本次改造目标是把 `创作意图` 从“自由填一句话即可继续”的弱入口，升级成“自由输入 + LLM 前置检查 + 明确补充建议 + 硬性解锁分析”的真实闸门。

具体目标：

1. 把创作意图输入控件升级为更适合表达的 3 行高 `textarea`。
2. 新增 `检查意图` 按钮，用独立 LLM 检查链路判断当前输入是否足够明确。
3. 检查不通过时，必须明确列出缺失维度，并给用户具体补充建议提示。
4. 在检查通过前，`分析选题` 按钮必须保持禁用。
5. 用户一旦修改创作意图文本，之前的检查结果自动失效，必须重新检查。
6. 保持 `topic_gate` 现有“保存简报 → 分析选题 → 风格与决策确认”的工作区骨架，不新增新页面，不复用通用 runner 外壳。

## 3. 非目标

本次不做以下事项：

1. 不把自由输入改成多字段重表单。
2. 不让检查器直接帮用户改写整段创作意图。
3. 不把“检查意图”和“分析选题”合并成一个按钮。
4. 不改变 `topic_analysis` 的评分、风格候选与决策建议逻辑。
5. 不改动下游 `design / storyboard / video_prompts` 的产物契约。

## 4. 推荐方案

推荐采用“引导补全型前置闸门”：

1. 用户仍然使用自由文本描述创作意图。
2. `保存选题简报` 负责写入 `topic_brief`，不负责判断内容是否充分。
3. 新增 `检查意图` 专用动作，走独立 LLM 检查链路。
4. 检查器只回答三类问题：
   - 是否通过
   - 缺少哪些方面
   - 每个缺失项建议如何补充
5. 检查通过后才允许点击 `分析选题`。
6. 如果用户修改了创作意图文本，之前的检查状态立即失效，重新回到“待检查”。

这样做的原因：

1. 它和现有 `分析选题` 职责清晰分离，不会让用户分不清“检查够不够”和“分析值不值得做”。
2. 它比单纯文案提醒更强，能真正阻止信息不足的输入继续流入后续阶段。
3. 它比结构化大表单更轻，仍保留了当前产品“先自由写”的自然入口。

## 5. 用户体验设计

### 5.1 工作区顺序

`topic_gate` 调整后仍保持三段式结构，但 `选题简报` 内部增加一层子闸门：

```text
选题简报
  - 创作意图输入
  - 保存选题简报
  - 检查意图
  - 检查结果 / 补充建议
    ↓
分析选题
  - 检查通过后解锁
    ↓
风格与决策确认
```

### 5.2 输入控件

当前单行 `input` 升级为 3 行高 `textarea`。

理由：

1. 用户不再被“桥段、热点、改编想法或一句话选题”暗示只能写一句。
2. 新手更容易自然补上背景、目标、风格倾向和限制条件。
3. 视觉上也更像“写创作方向”，而不是“填一个标题”。

### 5.3 按钮关系

`选题简报` 区块内存在两个动作：

1. `保存选题简报`
   - 主责：把当前文本和时长参数写入 `topic_brief`
2. `检查意图`
   - 主责：判断输入是否足够支撑整段视频方向

二者关系：

1. 推荐流程是“先保存，再检查”。
2. `检查意图` 依赖已保存的 `topic_brief`，避免前端本地状态和产物状态不一致。
3. `分析选题` 不再只依赖 `topic_brief` 存在，还依赖 `intent_check` 通过且未过期。

### 5.4 检查结果区

在 `创作意图` 输入区下方新增状态反馈卡，分四种状态：

#### 未检查

- 中性提示
- 文案示例：`先保存并检查创作意图，确认方向足够明确后再分析选题。`

#### 检查中

- 显示轻量 loading / inline busy
- 文案聚焦：`正在判断这段创作意图是否足够支撑整段视频方向`

#### 检查未通过

- 使用警示卡
- 显示：
  - 未通过结论
  - 总体原因摘要
  - 缺失维度列表
  - 每个维度的补充建议提示
- 文案风格要像“创作教练”，不是报错栈

示例结构：

```text
还不能分析选题
当前描述还不足以稳定推导整段视频方向，请先补充以下内容：

1. 改编角度 / 叙事抓手
   建议提示：
   - 你最想从哪个冲突、反差或情绪切口切进去？
   - 如果只能保留一个记忆点，希望观众记住什么？

2. 风格倾向
   建议提示：
   - 更偏动画、实拍、纪实、夸张喜剧还是治愈感？
   - 画面上希望更像“故事演绎”还是“信息解说”？
```

#### 检查通过

- 使用成功卡
- 显示：
  - 通过结论
  - 一句确认摘要
  - “已解锁分析选题”的明确提示

### 5.5 分析选题的解锁规则

`分析选题` 在以下情况下禁用：

1. 没有 `topic_brief`
2. 没有 `intent_check`
3. `intent_check` 存在但 `status !== pass`
4. `intent_check` 对应的 `intentHash` 与当前简报中的 intent 不一致

禁用时必须显示明确原因，不允许只置灰不解释。

推荐文案：

- `请先保存选题简报，再检查创作意图。`
- `创作意图尚未检查通过，请先补齐缺失信息。`
- `你已修改创作意图，请重新检查后再分析选题。`

## 6. 检查标准

首版按 5 个固定维度判断创作意图是否足够明确：

1. `题材 / 核心内容`
   - 用户到底在讲什么事情、角色或素材
2. `表达目标`
   - 想达成什么表达效果，如搞笑、反差、科普、情绪共鸣、观点输出
3. `改编角度 / 叙事抓手`
   - 从哪个切口组织整段视频
4. `目标画面或风格倾向`
   - 至少要有粗粒度方向，如动画、实拍、纪实、夸张、治愈
5. `关键限制`
   - 必须保留什么、不能出现什么、面向谁、是否有额外时长或内容边界

判定规则：

1. 缺 2 项及以上，直接不通过。
2. 只缺 1 项，但整体表述仍然空泛，也不通过。
3. 通过时不要求五项都写成结构化字段，但必须足以让模型稳定理解视频方向。
4. 返回结果必须点名缺失项，禁止只说“信息不足”。
5. 每个缺失项必须带 1-2 条中文补充建议提示。

## 7. LLM 检查链路设计

### 7.1 新增独立能力

新增一条与 `analyzeTopicGate` 平行的独立能力，例如：

- IPC：`sceneforge:check-topic-intent`
- Service：`checkTopicIntent(...)`
- Analyzer：`createTopicIntentDirectLlmChecker(...)`

它与现有 `sceneAnalyzeTopicGate` 的关系：

1. `check-topic-intent` 只负责“能不能继续分析”
2. `analyze-topic-gate` 只负责“值不值得继续制作、风格候选是什么”
3. 两者输入可共享 `topic_brief`，但输出契约不同，不能混用

### 7.2 输入来源

必读：

- `topic_gate.topic_brief`

可选：

- `source_intake.source_material`
- `source_intake.adaptation_selection`

原因：如果项目从 `source_intake` 进入，原始素材上下文能帮助检查器更准确地判断描述是否足够。

### 7.3 输出契约

检查器输出 JSON，再由 service / renderer 转换成 Markdown 产物 `topic_gate.intent_check`。

建议包含字段：

```json
{
  "status": "pass",
  "summary": "当前创作意图已经足够明确，可以进入选题分析。",
  "missingDimensions": [],
  "suggestions": [],
  "checkedDimensions": [
    {
      "id": "core_content",
      "label": "题材 / 核心内容",
      "status": "present",
      "reason": "..."
    }
  ],
  "intentHash": "..."
}
```

未通过时：

```json
{
  "status": "needs_more",
  "summary": "当前描述还缺少改编抓手和风格倾向，继续分析容易导致后续产物跑偏。",
  "missingDimensions": [
    {
      "id": "narrative_hook",
      "label": "改编角度 / 叙事抓手",
      "reason": "..."
    }
  ],
  "suggestions": [
    {
      "dimensionId": "narrative_hook",
      "tips": [
        "你最想放大的冲突、反差或情绪点是什么？",
        "如果整段视频只能围绕一个记忆点展开，希望观众记住什么？"
      ]
    }
  ]
}
```

### 7.4 产物落盘

推荐把检查结果写为新的 support artifact：

- `topic_gate.intent_check`

原因：

1. 页面切走再回来时可恢复检查结果
2. 便于定位“为什么分析按钮被锁住”
3. 后续若接 telemetry、调试或导出，也有稳定事实源

### 7.5 过期机制

必须记录本次检查对应的 `intentHash`。

失效规则：

1. 当前 `topic_brief` 中的 intent 文本变化后，重新计算 hash
2. 若与 `intent_check.intentHash` 不一致，则视为 `stale`
3. `stale` 状态下：
   - `分析选题` 按钮重新禁用
   - 页面提示“你已修改创作意图，请重新检查”

## 8. Markdown 与解析约定

现有 `topic_gate` 主要依赖 Markdown 产物和 `scene-hitl-markdown` 解析，本次继续沿用同一路径。

新增建议：

1. `src/sceneforge/lib/topic-gate-form.ts`
   - 让 `buildTopicBriefMarkdown` / `parseTopicBriefForm` 支持多行 `intent`
2. `src/sceneforge/lib/scene-hitl-markdown.ts`
   - 新增 `buildTopicIntentCheckMarkdown`
   - 新增 `parseTopicIntentCheckFromMarkdown`
3. `topic_gate.intent_check` 使用稳定 section / key 结构，便于后续测试和兼容

建议 Markdown 结构：

```md
# 创作意图检查

status: needs_more
intent_hash: abc123
summary: 当前描述还不足以稳定推导整段视频方向。

## 缺失项
- id: narrative_hook | label: 改编角度 / 叙事抓手 | reason: 未说明从哪个切口讲
- id: style_direction | label: 目标画面或风格倾向 | reason: 未说明画面偏动画、实拍还是纪实

## 补充建议
- dimension_id: narrative_hook | tip: 你最想放大的冲突、反差或情绪点是什么？
- dimension_id: narrative_hook | tip: 如果只能保留一个记忆点，希望观众记住什么？
- dimension_id: style_direction | tip: 更偏动画、实拍、纪实、夸张喜剧还是治愈感？
```

## 9. 前端模块设计

### 9.1 `SceneGateBriefForm`

职责调整：

1. `input` 改为 `textarea`
2. 在不打破现有提交流程的前提下暴露“当前 intent 是否已变更”的信号
3. 当用户编辑 intent 时，清掉本地“检查已通过”的前端态
4. 继续保留总时长 / 每段时长配置

### 9.2 新的检查结果展示模块

建议新增轻量组件，例如：

- `SceneTopicIntentCheckPanel`

职责：

1. 触发 `sceneCheckTopicIntent`
2. 展示检查状态
3. 渲染缺失项与建议提示
4. 向 `SceneGateAnalysisPanel` 传递“是否已通过”的结果

不建议把这块硬塞进 `SceneGateAnalysisPanel`，否则“检查意图”和“分析选题”两条职责会在一个面板中混杂。

### 9.3 `SceneGateAnalysisPanel`

职责收敛：

1. 不再负责“信息是否足够”的前置判断
2. 只在 `intent_check` 通过时允许触发分析
3. 若未通过或已过期，展示禁用原因与引导文案

### 9.4 `SceneForgeStudio`

需要在 `topic_gate` 工作区中管理三类状态：

1. `topic_brief`
2. `intent_check`
3. `topic_analysis`

这三个状态的顺序依赖是：

`topic_brief` → `intent_check` → `topic_analysis`

## 10. 错误语义

新增检查链路后，错误语义要保持“产品提示”而不是“技术提示”。

只对用户显示以下几类：

1. 未保存简报
2. 检查模型未配置
3. 返回结构不完整
4. 检查失败，请稍后重试
5. 已修改创作意图，请重新检查

不要把内部 JSON 解析细节、模型栈信息直接抛给用户主界面。

## 11. 测试策略

### 11.1 核心行为

至少覆盖以下行为：

1. 多行 `intent` 能正确保存与回填
2. `intent_check` 未通过时，`分析选题` 禁用
3. `intent_check` 通过时，`分析选题` 解锁
4. 修改 `intent` 后，旧检查结果失效
5. 未通过结果会渲染缺失项与建议提示
6. 旧项目没有 `intent_check` 时不崩溃

### 11.2 适合的测试层

1. `topic-gate-form` 单测
2. `scene-hitl-markdown` 单测
3. checker analyzer/service 单测
4. renderer UI 测试
5. IPC contract 测试

### 11.3 好测试标准

1. 优先测用户可观察行为
2. 不测试内部 `useState` 细节
3. 不把实现细节绑死在某个 CSS class 上
4. 通过真实 Markdown / artifact 契约验证状态流转

## 12. 风险与取舍

### 12.1 建议提示可能过于空泛

应对：

1. prompt 中强制要求提示可直接拿来补写
2. 每条提示控制在一句中文问题或一句补充引导

### 12.2 检查过严导致用户挫败

应对：

1. 只用 5 个粗维度，不做过细审查
2. 缺失项要解释“为什么这会导致后续跑偏”

### 12.3 检查和分析职责混淆

应对：

1. 前端用独立面板和独立文案
2. 分析按钮明确写“分析选题”，不承担补全职责

## 13. 后续对 PRD / Issues 的意义

这次改造天然可拆成 3 个可独立规划的模块：

1. `创作意图输入与检查状态模块`
2. `topic intent checker 后端能力`
3. `分析选题解锁与过期联动模块`

这些模块既适合写入 PRD 的“实现决策”，也适合在后续 issue 拆分时做垂直切片。

## 14. 结论

本设计通过增加 `检查意图` 前置闸门，解决了 `topic_gate` 当前最核心的问题：新手可以写得更自然，但不能再带着过薄、过模糊的输入直接进入后续生成链路。

首版重点不是“让 AI 帮用户写”，而是：

1. 让用户知道缺了什么
2. 告诉用户怎么补
3. 在补齐之前，不允许继续分析

这能在最小改动现有工作区骨架的前提下，显著提升 `SceneForge` 后续产物的方向稳定性。
