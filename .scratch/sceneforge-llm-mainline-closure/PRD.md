# PRD：SceneForge LLM Mainline Closure

## 问题陈述

SceneForge 的 Direct LLM 主链已经从“概念可行”推进到了“可以真实跑通若干阶段”，但当前工作面仍然分散在多个包里：Flow Hardening、Support Pack、Continue & Run、Style Selector、Regenerate、Draft Refinement、Publish 等。若继续按单包顺序推进，容易出现两个问题：

1. 已经足够作为验收基线的包被重复投入。
2. 真正阻塞 LLM 完整闭环的项没有被统一识别和排序。

用户当前目标已经明确变化：**先把基于 LLM 的完整流程全都完善好，包括前后端、交互、流程运转与细节体验。**

## 解决方案

建立一个新的主线总包，对现有工作重新编排：

1. 识别哪些能力已经可以作为“已完成基线”。
2. 识别哪些缺口是当前必须实现的 LLM 主链阻塞项。
3. 识别哪些包虽重要，但不应抢占当前主线优先级。
4. 形成接下来逐项实现的统一顺序。

## 用户故事

1. 作为维护者，我想先看到一张完整的主链收敛图，以便知道下一步应该做什么，而不是继续在零散 backlog 里切换。
2. 作为维护者，我想区分“文档已齐全”和“产品已真正闭环”，以便把精力放在真实缺口上。
3. 作为维护者，我想把前后端、交互、状态流、验收点一次列清，以便后续每一票都能明确收口标准。
4. 作为维护者，我想让 ACP、Publish 这类非当前阻塞项排到后面，以便不影响 LLM 主链收敛。

## 实现决策

- 以 Direct LLM 主链为唯一当前主线。
- 先做盘点，再按盘点顺序逐项实现，不再按后续包的创建顺序机械推进。
- 前面已收口包按三类处理：
  - 已完成基线
  - 当前必须实现
  - 后续再做 / 暂缓
- ACP 对齐保持 deferred，直到 LLM 主链稳定收口。

## 测试决策

- 这包本身以文档与实施顺序为主，不直接引入运行时代码。
- 后续每个当前必须实现项都应能映射到至少一个自动化验证点和一个人工验收点。

## 超出范围

- ACP 多轮能力推进。
- Publish 工作区实现。
- 无人值守全链自动化。

## 进一步说明

- 本包是后续实现的总入口，不替代已有子包文档。
- 子包继续保留，但优先级与定位以本包为准。
