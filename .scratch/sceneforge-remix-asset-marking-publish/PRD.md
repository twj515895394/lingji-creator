# PRD: SceneForge Remix 资产标记与保存入库重构

## 问题陈述

当前 `SceneForge Remix` 原片资产处理工作台的第 05 步和第 06 步存在明显的语义错位。

从用户视角看，第 05 步“人工标注”页面正在表达一种“逐片段复核与修订”的工作方式：页面会展示当前片段、片段标题、时间范围，以及围绕某个片段展开的保留/替换建议。这会让用户自然地认为自己正在处理某个 `segment`，而不是在补齐整条视频资产的入库信息。

但从系统真实行为看，这一阶段当前持久化的内容只是资产级元数据，例如标签、备注和标记者信息；第 06 步“保存入库”也不是新的片段处理步骤，而只是对整条资产执行前置门禁校验后切换入库状态。结果就是：

1. 用户无法判断第 05 步到底是在“修片段”还是“补资产信息”。
2. 用户在第 06 步仍然看到片段级内容，难以理解点击“保存入库”之后系统究竟会保存什么。
3. UI 所表达的对象粒度与当前数据模型、持久化结构不一致，后续 PRD、开发、测试和资产检索都容易继续跑偏。

如果不尽快纠正，第 05 / 06 步会持续把“资产入库”误导成“片段级人工审片”，让这条工作流难以稳定扩展，也会给后续从 JSON 迁移到 SQLite 带来额外清理成本。

## 解决方案

将原片资产处理工作台的第 05 / 06 步统一重构为**资产级工作流**。

- 第 05 步从“人工标注”改名为 `资产标记`。
- 第 05 步只承载整条视频资产的标签、备注、标记者等信息编辑，不再展示某个片段的详情、时间范围、保留/替换建议等片段级内容。
- 第 06 步保留 `保存入库`，作为资产处理流程的最终收口页。
- 第 06 步展示前置门禁状态、资产标记摘要、预计保存结果，以及显式的 `保存入库` 操作按钮。
- 点击 `保存入库` 时，系统只执行资产级确认与持久化动作：校验前置条件、回写资产状态、更新时间戳与相关元数据，并将结果保存在现有 JSON / 文件目录结构中。

本次改造不引入新的数据库，也不改造 Remix Variant 与 SceneForge 草稿域的持久化。资产库域继续使用现有 `source asset manifest + 衍生 JSON artifact` 的方式表达，确保现在的输出足够结构化，方便未来在资产库域单独迁移 SQLite。

## 用户故事

1. 作为素材处理操作员，我想在第 05 步看到的是“整条视频资产”的标记信息，而不是某个片段的信息，以便我明确自己此时是在补入库资料。
2. 作为素材处理操作员，我想在第 05 步只处理标签和备注，以便快速完成资产入库前的人工补充，而不是再次进入片段级审片流程。
3. 作为素材处理操作员，我想明确知道第 05 步保存的是资产标签、资产备注和标记者信息，以便我理解这些信息后面会如何被资产库使用。
4. 作为素材处理操作员，我想在第 05 步看到 AI 已经整理好的资产级建议提示，但最终只需要决定保留哪些标签、是否补备注，以便降低录入心智负担。
5. 作为素材处理操作员，我想在第 05 步不再看到“当前播放片段”“片段 01”之类的卡片，以便减少对象粒度错乱造成的困惑。
6. 作为素材处理操作员，我想在第 06 步看到完整的前置门禁 checklist，以便确认导入、切片、关键帧、原片理解、资产标记都已经满足入库要求。
7. 作为素材处理操作员，我想在第 06 步看到“资产标记摘要”，以便在最终入库前核对标签和备注是否符合预期。
8. 作为素材处理操作员，我想在第 06 步明确看到点击“保存入库”会发生什么，以便放心执行最终入库动作。
9. 作为素材处理操作员，我想在前置门禁未满足时看到为什么不能入库，以便知道还缺哪一步。
10. 作为素材处理操作员，我想在点击“保存入库”后看到成功反馈和状态变化，以便确认这条资产已经进入可复用资产库。
11. 作为素材处理操作员，我想在保存入库后，从资产库列表里以已发布状态看到这条资产，以便后续在二创流程中复用。
12. 作为产品设计者，我想让第 05 / 06 步和真实数据模型保持一致，以便后续 PRD、开发和测试围绕统一语义演进。
13. 作为前端开发者，我想让第 05 / 06 步都使用资产级视图模型，而不是临时拼接片段级说明，以便组件职责更稳定。
14. 作为后端/Electron 层开发者，我想继续复用现有 `SourceAsset` 与 `published_to_library` 状态模型，以便最小改动完成本期重构。
15. 作为测试维护者，我想让第 05 / 06 步的门禁、保存、发布、摘要展示行为有明确的自动测试覆盖，以便防止 UI 和持久化再次出现语义漂移。
16. 作为未来架构维护者，我想让当前资产库关键信息都以稳定 JSON 结构表达，以便未来只对资产库域做 SQLite 迁移。
17. 作为二创创作者，我想在后续选择已入库素材时读取到清晰的资产标签和备注，以便更快筛选可用素材。
18. 作为项目维护者，我想让 Remix Variant 和 SceneForge 草稿域维持当前草稿式持久化，以便本期不把范围扩散到无关域。

## 实现决策

- 第 05 步正式更名为 `资产标记`，并统一替换导航、页头、状态文案、摘要文案中的旧称呼。
- 第 05 步只表达资产级对象，不再显示当前片段、片段标题、时间范围、片段保留/替换建议等内容。
- 第 05 步保留“AI 预填 + 人工修正”的思路，但预填内容只作为资产标签与备注的建议来源，不再作为片段审阅工作台。
- 第 05 步的完成判定调整为面向资产级最小必填集。推荐以“至少 1 个标签”为硬门槛，备注为可选但鼓励填写；最终语义必须与门禁校验、状态文案、按钮禁用态保持一致。
- 第 06 步保留为显式确认页，而不是自动入库或隐式入库。
- 第 06 步主界面需要包含三块信息：前置门禁 checklist、资产标记摘要、最终保存动作区。
- 第 06 步仍然基于现有入库服务执行，不额外引入新持久化后端；其职责是对现有资产 document 做状态切换与元数据回写。
- 资产库域继续使用 JSON / 文件目录持久化，`SourceAsset` 仍是资产库主实体。
- `SourceAsset` 上的资产级字段继续承担标签、备注、标注来源、时间戳、状态等职责；本期不引入新的片段级人工标注 schema。
- Snapshot 继续作为运行时视图数据，不单独持久化。
- Remix Variant 域与 SceneForge 草稿域不纳入本期持久化重构，仍按现有草稿式文件结构运行。
- 为未来 SQLite 迁移预留边界：只有资产库域需要保证 JSON 结构可稳定映射为关系模型；二创与草稿域不在本期建模范围内。
- 推荐抽出稳定深模块：
  - `资产标记完成判定模块`：集中定义第 05 步的最小必填语义和提示文案。
  - `入库门禁汇总模块`：集中生成第 06 步 checklist 与阻塞原因。
  - `资产入库摘要模块`：集中生成第 06 步显示的标签、备注、统计与预计保存结果。
  - `源资产发布持久化模块`：封装入库状态切换与 manifest 回写，避免 UI 层拼接持久化细节。

## 测试决策

- 好测试应该只验证外部行为和稳定契约，不验证组件内部实现细节或临时 DOM 结构。
- 必须为第 05 步和第 06 步的资产级语义提供自动测试，重点覆盖：
  - 阶段文案和门禁状态与资产级语义一致。
  - 第 05 步保存标签和备注后，资产元数据被正确回写。
  - 第 06 步只在前置条件满足时允许入库。
  - 点击 `保存入库` 后，资产状态切换为已发布并回写持久化结果。
  - 已发布资产在后续视图中能暴露正确的标签、备注和状态。
- 需要测试的模块包括：
  - 第 05 / 06 步页面级状态机和提交行为。
  - 资产标记完成判定与入库门禁汇总逻辑。
  - 资产入库摘要构建逻辑。
  - 入库持久化服务与 mock API 契约。
- 测试应优先复用现有 Remix service、validator、mock data、workspace snapshot 相关测试模式，保持与仓库已有 Vitest 风格一致。
- 手动验收需要覆盖：
  - 前 1-4 步已完成时，第 06 步显示可执行入库按钮。
  - 第 05 步未满足门禁时，第 06 步阻塞态和提示文案正确。
  - 第 05 步和第 06 步都不再出现片段级卡片。
  - 入库后回到资产库能看到状态变化。

## 超出范围

- 不重构第 01-04 步的主流程与核心算法。
- 不新增片段级人工标注系统。
- 不在本期引入 SQLite 或其它数据库持久化。
- 不重构 Remix Variant 的草稿式持久化。
- 不重构 SceneForge Studio / SceneForge 草稿域的数据模型。
- 不实现复杂资产检索、筛选器改造或资产推荐系统。
- 不做历史资产的批量迁移脚本。
- 不在本期修改后续二创消费端的完整交互，仅保证其可继续读取既有资产字段。
