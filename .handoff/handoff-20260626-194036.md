# Handoff - 解决项目类型物理误篡改及纠偏

本交接文档记录了关于 **SceneForge Remix 二创工作流（视频抽帧、首尾帧阈值控制、物理路径渲染）** 的开发进展，并对最近遇到的 **“普通工坊项目在首页全被误显示为 Remix 二创”** 的严重问题进行了深度诊断，提供了明确的后续修复与恢复计划。

---

## 1. 核心进展总结

### 1.1 关键帧提取精确抽帧优化
* **FFmpeg 寻道优化**：在 [remix-keyframe-service.ts](file:///Users/tangwujun/Documents/trae_projects/lingji-creator/electron/sceneforge/remix/remix-keyframe-service.ts) 中对极短的分镜 `clip` 源采用**输出寻道**（`-ss` 位于 `-i` 之后），对 `source` 大视频源保持输入寻道但追加 `-accurate_seek`。解决了抽出来的首帧、中帧、尾帧画面完全重复的问题。
* **时限阈值过滤**：后端增加了 `minDurationForMiddleFrameSec` 时长阈值过滤，小于阈值（默认 8 秒）只提首尾帧，大于等于才提中间帧。前端 [RemixAssetProcessing.tsx](file:///Users/tangwujun/Documents/trae_projects/lingji-creator/src/sceneforge/remix/pages/RemixAssetProcessing.tsx) 中增加了参数交互输入与 IPC 参数绑定。

### 1.2 前端图像相对路径失效修复
* **路径动态组装**：修改 [RemixFrameImage.tsx](file:///Users/tangwujun/Documents/trae_projects/lingji-creator/src/sceneforge/remix/components/RemixFrameImage.tsx)，当关键帧为相对路径且传入 `projectDir` 时，自动在 `toFileSrc` 转换前拼接绝对路径，修复了 `file:///sceneforge` 协议下的加载失败报错。
* **属性透传**：在相关的 `<KeyframeGallery>`、`<EditedKeyframeStepPanel>` 组件层完成了 `projectDir` 的逐级透传。

### 1.3 最近项目列表强校验与纠偏
* **物理文件为真理源**：在 [recent-projects.ts](file:///Users/tangwujun/Documents/trae_projects/lingji-creator/electron/recent-projects.ts) 的 `addRecentProject` 与 `refreshRecentProjects` 接口中，根据物理文件 `project.json` 中实际的 `pipelineId === 'reference_remake'` 作为唯一标准判定工程是否为 `'remix'`，并自动重写纠偏 `recent-projects.json` 中的错误缓存。
* **启动即刷新**：修改了 [electron/main.ts](file:///Users/tangwujun/Documents/trae_projects/lingji-creator/electron/main.ts) 的 `load-recent-projects` IPC 处理器，使其在启动拉取列表时顺便触发 `refreshRecentProjects` 物理纠偏与刷新菜单，确保首页加载即纠偏。

## 2. 严重问题深度诊断：为什么普通项目全变成了 Remix？

### 2.1 故障现象
重启客户端后，不仅真正的二创项目（如 `remix100`）恢复为了 `Remix 二创` 标签，其他原本为普通工坊的老项目（如 `test001`-`test005`，`test`，`sceneforge-acceptance-` 等）也**全部被加上了 `Remix 二创 · 资产入库` 标签**。

### 2.2 根本原因定位（物理文件是如何被篡改的？）
通过读取 `test005/project.json` 物理文件，发现磁盘上的物理工程数据确实被写成了：
```json
  "type": "sceneforge",
  "sceneforge": {
    "pipelineId": "reference_remake",
    ...
  }
```
顺藤摸瓜排查到物理文件的读取与数据升级类：[electron/project-file.ts](file:///Users/tangwujun/Documents/trae_projects/lingji-creator/electron/project-file.ts)：
```typescript
function normalizeRecoveredSceneProjectMeta(
  meta: Partial<SceneProjectMeta> | undefined,
  state: SceneStateSnapshot,
): SceneProjectMeta {
  return {
    version: 1,
    projectRoot: 'sceneforge',
    pipelineId:
      meta?.pipelineId ??
      (state.pipelineId === 'original_scene' || state.pipelineId === 'prompt_pack_only'
        ? state.pipelineId
        : 'reference_remake'), // ← 致命错误：缺省时默认设为了 reference_remake
    ...
  }
}
```
1. **老项目无字段**：在 2.0 版本或较早前创建的老工坊项目（如 `test001`）没有定义过 `pipelineId` 这个新字段（`meta?.pipelineId` 与 `state.pipelineId` 均缺省/不存在）。
2. **错误兜底偏心**：上述代码在两者都缺省时，自作聪明地直接将 `pipelineId` 默认回退返回为 **`'reference_remake'`**（二创项目），而不是工坊原生模式 `'original_scene'`。
3. **回写磁盘污染**：在加载工程的升级链路 `hydrateExistingProjectData` 中，由于检测到内存元数据与磁盘不一致，系统直接调用了 `writeProjectJson` **把这个污染过的 `reference_remake` 物理回写并写死到了磁盘上的 `project.json` 文件**！
4. **纠偏检测受骗**：主进程刷新最近项目列表时，以物理文件内容作为真理源读取，由于被污染的 `project.json` 确实声明了自己是 `'reference_remake'`，导致普通的 SceneForge 老项目也全被错误识别并刷成了 `Remix 二创`。

## 3. 下一步执行与修复方案（待办事项）

接手的代理需要**立即**实施以下修复步骤：

### 任务 1：修复 project-file.ts 加载逻辑（切断篡改源）
* **修改目标**：[electron/project-file.ts](file:///Users/tangwujun/Documents/trae_projects/lingji-creator/electron/project-file.ts) 的 `normalizeRecoveredSceneProjectMeta` 函数。
* **修改方案**：当 `pipelineId` 缺省时，必须默认归类为普通的工坊原生模式 **`'original_scene'`**，不应偏心回退为 `'reference_remake'`。
  ```diff
      pipelineId:
        meta?.pipelineId ??
  -     (state.pipelineId === 'original_scene' || state.pipelineId === 'prompt_pack_only'
  +     (state.pipelineId === 'reference_remake' || state.pipelineId === 'prompt_pack_only'
          ? state.pipelineId
  -       : 'reference_remake'),
  +       : 'original_scene'),
  ```

### 任务 2：恢复被污染的物理文件
* **背景**：因为之前的物理文件加载已经把 `'reference_remake'` 写死了部分老项目的 `project.json` 中，如果不还原这批物理文件，它们在磁盘上依旧会被当成二创。
* **还原方案**：
  * **方案 A（Git 还原）**：如果这些测试项目有纳入 Git 管理，可直接对 `project.json` 执行 git 撤销或 checkout。
  * **方案 B（批量脚本纠正）**：编写一个临时的 Node.js 修复脚本（存放在项目根目录），遍历 `recent-projects.json` 中所有的项目目录：
    * 若该工程其实是普通工坊流程（可以通过检查其 `entryPath !== 'source_intake'`，或者本来就属于 `test001`-`test005` 等测试目录），将其 `project.json` 中的 `sceneforge.pipelineId` 重新改写还原为 `'original_scene'`。
    * 重新清空/刷新最近项目列表中的 `projectKind` 缓存并写入。

### 任务 3：单元测试与整合回归
* 跑通最近列表测试 `npx vitest run tests/recent-projects` 验证其行为。
* 重启客户端，检验欢迎页上各项目是否能够完美按物理文件划分成 `Remix 二创`（如 `remix100`） and 普通的 `SceneForge`（如 `test001` 等老工坊项目），互不干扰。
