## 3. 当前主线判断

### 3.1 已经确认的方向

- **主链是 LLM，不是 ACP。**
- **ACP Studio Alignment 先保留为待做，不插入当前实现队列。**
- 当前剩余工作应全部围绕一个判断标准：
  - **是否阻塞 LLM 主链从 Run → 审阅 → 提交 → Validate → Continue → 下一阶段继续运行 的稳定闭环。**

### 3.2 当前最重要的结构性结论

1. 之前 LLM 产物质量不稳，并不只是“模型本身差”，很大概率和运行时 prompt 没完整带上规范、旧 skill 关键标准没迁完有关。
2. 上述问题本轮已做第一轮系统修复，但还没完成整链产品级闭环。
3. 现在最该做的不是再开新包，而是把 **断点修复 + 验收清单闭环** 做完。

## 4. 待办优先级

下面按“必须继续做的顺序”列清楚，并标注 **先编码 / 先补文档 / 先人工验收**。

### P0：草案生成、提交、校验、审批、继续之间的断点修复

- 类型：**先编码**
- 原因：这是当前总计划里最明确、也最影响主链体验的剩余工程项。
- 建议切入点：
  - `src/sceneforge/components/stage-run/StageRunPanel.tsx`
  - `src/sceneforge/pages/SceneForgeStudio.tsx`
  - `src/sceneforge/hooks/useSceneStageContinuation.ts`
  - `electron/sceneforge/service.ts`
  - 相关校验/状态流测试
- 重点检查：
  - submit 失败时草案是否稳定保留
  - validate / approve / continue 的按钮禁用原因是否准确
  - continue 后阶段切换、当前阶段持久化、默认产物回显是否连贯
  - continue / continue & run 是否与 validate 状态严格联动
- 文档动作：实现后同步主计划与 issue，不要先单独补新设计稿

### P1：把“验收清单中尚未由产品和代码共同闭环的环节”补齐

- 类型：**先编码，再补验收文档**
- 原因：这项不是纯文档，应该基于当前真实代码状态把剩余缺口修到可验收。
- 建议方式：
  - 先列一个最小验收矩阵，覆盖 direct_llm 主链阶段
  - 遇到真正阻塞验收的缺口，立即回到代码修复
  - 修完后再补齐清单与结论
- 更像是：
  - `Direct LLM E2E checklist-driven repair`
  - 不是先写长文档再说

### P2：同步更新主线总计划，让文档状态和代码现实一致

- 类型：**先补文档**
- 范围：
  - `.scratch/sceneforge-llm-mainline-closure/IMPLEMENTATION-PLAN.md`
- 需要补的点：
  - Task 1 的基线确认要补齐
  - Task 3 的“Publish 下调、ACP deferred、后续票都回映射到 LLM 主链”要明确勾状态
  - Task 4 的“逐项实现入口、代码触点、测试命令、人工验收点”要补完整
- 说明：这是重要但不阻塞编码，可放在 P0/P1 某个子项结束后穿插完成

### P3：做一轮真机 Electron 连续验收

- 类型：**先人工验收，代理辅助修 bug**
- 建议验证链路：
  - reference → story → assets → design → script → performance → storyboard → audio → video_prompts
  - 每阶段至少覆盖：Run、草案审阅、补充优化、提交、Validate、Continue
- 特别关注：
  - Continue 后是否即时进入新阶段
  - 草案保留与重新生成是否串台
  - 默认产物回显是否稳定
  - 80k token 超限报错是否清晰
- 结果处理：
  - 发现问题后，按单缺陷单修复收口，不要把真机问题和新功能开发混在一起

### P4：保持 deferred / postponed 状态，不要误开新战线

- 类型：**先补文档状态，暂不编码**
- 包含：
  - ACP Studio Alignment：`deferred`
  - Publish Workspace：下调到 LLM 主链稳定之后
- 原则：
  - 这两项现在都不该抢占主链优先级
