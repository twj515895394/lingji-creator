## 这次真正解决了什么

### 1. storyboard 现在已经“真实打通”

不是只靠测试通过，而是用户在真实项目 `test002` 上反复联调后，当前结论是：

- `storyboard` 阶段可以正常生成 4 个核心产物。
- 可以提交草案到产物库。
- 当前校验可以通过。

这意味着之前反复出现的几类问题已经被压住：

- 只生成首个 artifact，缺少其余 artifact。
- 中文要求漂移成全英文正文。
- 多包逻辑不遵守，或只给一个全局 prompt。
- `control_board_prompts` / `style_board_prompts` 未继承已定稿 storyboard，发生内容漂移。
- 缺失 `Control-Oriented Storyboard Board` / `Style & Rendering Storyboard Board` 这类固定 marker，导致提交校验失败。

### 2. 本轮 storyboard 有效修复手段

后续阶段建议复用同样思路，而不是重新猜：

1. 把 stage 拆成更小的 direct-llm 调用，不要求一次把所有 artifact 全吐完。
2. 第一轮先定稿核心主包，再把后续 artifact 建立在“锁定摘要”上，而不是反复把全量 stageContext 塞给模型。
3. 把关键规则不只写在文档里，而要真正进入：
   - stage prompt
   - follow-up hard rules
   - output contract / required markers
   - 测试断言
4. 对容易被模型漏掉的固定结构 marker，必要时在 runner 侧做轻量兜底，而不是把稳定性完全赌在模型自觉上。
5. 先加日志看“喂给 LLM 的实际 prompt”和“stageContext 长什么样”，再判断是不是上下文漂移，而不是凭感觉改 validator。

### 3. 这次新增/强化的 storyboard 能力点

本轮围绕 storyboard 强化过的能力主要包括：

- 中文主导输出约束。
- 多包规则与 pack coverage 约束。
- control/style 分别单独生成，避免单次输出丢键。
- 锁定摘要继承，降低上下文膨胀和题材漂移。
- `control_board_prompts` / `style_board_prompts` 的正式整板 marker 强约束。
- 画面区专业描述维度强化，不再只剩红蓝箭头。
- 多 Pack 交界镜头/衔接策略约束。
- runner 侧对控制板/风格板整板标题的兜底补位。

## 下一次会话建议顺序

### 1. 先把“storyboard 这轮的检查框架”抽成后续阶段通用检查清单

建议对后续每个阶段都检查下面几类问题：

- 生成前送进 LLM 的 prompt 是否真的带上了阶段规则。
- 是否存在中文主导要求失效、正文英文化。
- 是否存在一次调用丢 artifact、只吐首个 key。
- 是否存在 stageContext 太大导致漂移。
- 是否存在 marker/固定 section 漏写，导致提交草案或校验失败。
- 是否存在后续 artifact 没有严格继承上游已定稿内容。

### 2. 优先测 `audio`

原因：它在 `storyboard` 后面，且相对比 `video_prompts` 更短链，适合作为下一站。

重点检查：

- 是否严格继承上游 design / storyboard 已定稿内容。
- 是否中文主导。
- 是否完整输出 `BGM / Foley-SFX / Ambience / Silence` 等结构。
- 是否存在“只吐一部分字段”或 section 丢失。
- 是否存在提交草案时的固定 marker / contract 校验问题。

### 3. 再测 `video_prompts`

这是后续最关键、也最可能复现 storyboard 同类问题的阶段。

重点检查：

- 默认是否只生成正式主交付，而不是多余英文包。
- `video_prompt_pack_plan` 是否写清 storyboard packs / segment / VGU 覆盖关系。
- 是否真的引用 `control_board_prompts` 与 `style_board_prompts` 作为关键帧参考，而不是只提 `storyboard_prompt_pack`。
- 是否存在中文主导失效、正文英文化。
- 是否存在 prompt 过大导致内容漂移或只输出部分 artifact。
- 如果失败，优先按 storyboard 的办法：
  - 看 prompt 日志
  - 看 required marker
  - 看是否适合拆 phase
  - 看是否需要固定标题/section 兜底

### 4. 最后测 `export/publish`

重点不是内容生成，而是消费与展示：

- UI 是否能正确查看/复制核心产物。
- 导出包是否使用了新的主交付 key。
- 不要因为上游 key 迁移或 section 变更，导致展示区拿不到内容。
