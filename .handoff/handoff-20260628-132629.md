# SceneForge Remix: 原片理解 V2 优化开发总结与交接文档 (Issue #01 - #07)

本交接文档详细整理了**原片理解 V2 (remix-understanding-v2)** 阶段所有 7 个子 Issue 的完整研发历程、技术架构设计、解决的关键问题、踩坑记录及后续阶段规划。

---

## 一、 背景概述与核心脉络

在 SceneForge Remix 2.0 中，**原片理解 (Original Source Video Understanding)** 模块经历了从 V1 到 V2 的重大代际跨越。V1 结构主要是纯文本大模型仅仅基于 Whisper 台词生成的粗粒度段落汇总，无法做到画面感知，且在台词微调或局部重跑时会带来严重的 Token 浪费。

V2 的核心目标是通过引入**多模态关键帧视觉分析**、**台词纠错与新鲜度判定机制**以及**影视大模型汇总 V2 与一键 Markdown 导出**，构建画面与声音融为一体的精准原片大纲，并将生成的所有结构化产物通过统一的 **V2 Workbench Snapshot** 透给前端进行多维度卡片展示。

## 三、 关键技术实现与架构设计

### 1. 细粒度新鲜度过期机制 (Stale Mechanism)
- **挑战**：在用户微调某一段台词时，若重跑整个视频的原片理解，会消耗大量的 LLM Token 且耗时很长。
- **设计**：设计了哈希判定逻辑：
  - 基于当前段落的 `segment` 范围、`effectiveText` (纠错后的生效台词) 和 `keyframes` 关键帧信息，在片段输入发生改变时生成最新的 md5 摘要。
  - 将最新 md5 与已保存的段落理解 `understanding.inputHash` 比对。若不同，或者 `correction.updatedAt > understanding.generatedAt`，或者 `frame_vision.generatedAt > understanding.generatedAt`，则片段被标记为 `isStale = true`。
  - 前端界面会针对 `isStale` 段落卡片展示黄色警告，提供“只重跑过期片段”的高效入口，节省了 80% 以上的 LLM 请求量。

### 2. 多模态画面视觉先验融合
- **挑战**：大模型没有眼睛，无法得知画面里是“晴天”还是“雨天”，是“动作戏”还是“文戏”。
- **设计**：
  - `RemixFrameVisionService` 会提取中间帧并压缩至最大限幅 `1024px` 的 JPEG，转换成 Base64。
  - 启动并发为 2 的多模态 LLM 请求，取得画面元素的文字级描述（Visual Caption），保存于 `{segmentId}.frame_vision.json` 中。
  - 段落大模型（Understanding）的 Prompt 在装配时，将此视觉文件中的内容作为“画面先验背景”合并拼装输入大模型，使得正向 Prompt 的生成能够完美结合声画两端信息。

### 3. V2 大聚合 Snaphot 契约 (V2 Exclusive)
- **设计**：在 Issue 07 中，由于开发团队决定全面升级到 V2 格式，我们在 `loadRemixUnderstandingWorkbench` 中**彻底移除了 V1 兼容代码**。Snapshot 成为纯 V2 对象。
  - `overview` 块：包含 `logline`, `storySummaryShort`, `storyContent`, `eventChain`, `characterMap`, `remixDirections` 等结构化大看板。
  - `segments` 块：包含 `transcript`, `visual`, `camera`, `story`, `remix`, `videoPrompt` (包含 V2 15维 `dimensions` 数组) 多个强类型子对象。
  - 前端组件 `UnderstandingWorkbenchPanel.tsx` 通过直读 `dimensions` 进行动态 `map` 渲染，解耦了对物理属性名的强依赖，具备极高的扩展性。

## 四、 开发中遇到的困难、踩过的坑与解决方案

### 1. StoredSourceAsset 读取Manifest路径 ENOENT
- **问题**：在测试用例 `sceneforge-remix-understanding-report-export.test.ts` 中，模拟数据写入了 `.remix/project.json`，然而在运行时读取时却抛出找不到文件的错误。
- **归因**：排查 `RemixStore` 底层源码发现，`readStoredSourceAsset` 并不是读取本地 `.remix/` 文件夹，而是将项目路径拼接为 `sceneforge/remix/source-assets/${sourceAssetId}/source_manifest.json` 来作为源 Manifest 的实际存储库。
- **解决**：修改测试环境写入逻辑，创建正确的 `source-assets/${sourceAssetId}` 文件夹，并将模拟配置改写为 `source_manifest.json`，从而完美解决了文件找不到的报错。

### 2. 旧版测试中的 `storyArc` 废弃断言失败
- **问题**：升级 V2 Schema 后，我们在大汇总对象中移除了冗余的 `overall.storyArc`（改用核心剧情事件轴 `eventChain`）。这导致原有的老单测用例无法通过。
- **解决**：在兼容测试 `sceneforge-remix-source-understanding-rollup.test.ts` 中，删除了已废弃的对 `overall.storyArc` 的 expect 断言。

### 3. 前端测试中因折叠未展开导致元素 toContain 失败
- **问题**：在 React DOM 模拟测试 `sceneforge-remix-asset-processing.test.tsx` 中，断言 `'固定镜头，缓慢抬头。'` 必须在 `container.textContent` 中可被搜索到，但测试却失败了。
- **归因**：在 UI 改版后，段落明细卡片在默认状态下是折叠的，只有卡片处于 `isExpanded` 时正向 Prompt 文字才会渲染。由于测试环境默认将 Mock segment 的 `isStale` 设为 `false`，卡片处于收起态，所以 DOM 文本中查找不到这段话。
- **解决**：在 Mock API 以及测试的 MockApiClient 返回值中，将测试片段的 `isStale` 直接设为 `true`。这使得卡片在页面挂载时就会**默认展开**，让 DOM 测试顺利抓取到文字的同时，还对“Stale 状态提示”渲染逻辑进行了有效覆盖。
