## 二、本次新增问题：分镜片段分辨率 / 源素材元数据核查

### 结论先说

对 `remix100` 的实测结果是：

1. **没有证据表明当前 segment clip 再次把真实源视频缩小了分辨率。**
2. **当前工程更大的问题是：`source_manifest.json` 中的 `videoMetadata` 很可能是写死默认值，不是真实探测结果。**
3. **当前切片虽然保分辨率，但不是“原码流/母版级保存”；它是 `libx264` 重编码产物。**

### 实测证据

实测对象：

- 源视频：`/Users/tangwujun/Pictures/华强买瓜原视频【4K_120FPS】无水印 - 1.lv_0_20260530125933(Av116662804158126,P1).mp4`
- 抽样切片：`.../source_segments/segment-004/source_clip.mp4`

`ffprobe` 抽样结果：

- 源视频实际：`852x480`、`yuv420p`、约 `30fps`
- `segment-004/source_clip.mp4`：`852x480`、`yuv420p`、`30fps`

但同一个 source asset 的 manifest 中记录为：

- `videoMetadata.width = 1920`
- `videoMetadata.height = 1080`
- `videoMetadata.fps = 25`

这说明：

- 用户在 UI 中看到的“素材规格”当前并不可信
- 很容易误判成“切片被压缩”
- 真实原因更可能是 **source metadata 采集阶段就写错了**

### 代码分析

#### 1. 真正缩图的只有 frame vision 输入图

[remix-frame-vision-service.ts](/Users/tangwujun/Documents/trae_projects/lingji-creator/electron/sceneforge/remix/remix-frame-vision-service.ts) 内有：

- 当图片大于 `1024` 时 resize 到 `1024`

这只影响：

- LLM 画面理解输入
- 占用与推理成本

不影响：

- `source_clip.mp4`
- 原始 keyframe 文件落盘分辨率

#### 2. segment clip 当前使用重编码，但未主动 scale

[segment-clip-service.ts](/Users/tangwujun/Documents/trae_projects/lingji-creator/electron/sceneforge/remix/segment-clips/segment-clip-service.ts) 当前 `reencode_accurate` 参数为：

- `-c:v libx264`
- `-preset veryfast`
- `-crf 18`
- `-c:a aac -b:a 128k`
- `-pix_fmt yuv420p`

没有发现：

- `scale=...`
- `-s WxH`

因此当前逻辑是：

- **保留原分辨率输出**
- 但 **重新编码**
- 所以并非“母版直存”

#### 3. source asset 元数据当前是硬编码默认值

[remix-source-asset-service.ts](/Users/tangwujun/Documents/trae_projects/lingji-creator/electron/sceneforge/remix/remix-source-asset-service.ts) 在 `createFromImport()` 中直接写入：

- `width: 1920`
- `height: 1080`
- `fps: 25`
- `audioChannels: 2`
- `hasAudio: true`

这就是本次误导用户判断的根因。

## 三、对“保存入库时应保存真正原分辨率分片吗”的建议

### 我的建议

建议拆成两层资产，不要混用一个 `source_clip.mp4` 试图同时满足“分析轻量化”和“资产库母版引用”：

1. **分析层产物**
   - 保留当前轻量策略
   - 关键帧可继续允许缩图供理解使用
   - 分镜 clip 可继续用当前 `reencode_accurate`

2. **入库层 / 可复用层产物**
   - 保存“发布级 source clip”
   - 要求至少保证：
     - 真实源分辨率
     - 真实帧率
     - 明确记录生成模式
   - 最好额外区分：
     - `analysis_clip`
     - `master_clip`

### 如果只做最小整改

最小可落地方案：

1. **立即修 source video metadata 探测**
   - 创建 source asset 时用 `ffprobe` 真实读取 `width/height/fps/audioChannels/hasAudio`
   - 纠正 UI、manifest、SQLite 中的展示值

2. **给 clip generation report / asset artifact 增加媒体规格字段**
   - 把每个 clip 的真实 `width/height/fps/codec/size` 记录下来
   - 以后用户核对资产时可直接看到“母片 vs 分片”是否一致

3. **在“保存入库”前加一次媒体规格校验**
   - 若 source metadata 与真实文件不一致，提示修正或自动回填
   - 若 clip 与源视频规格不一致，也明确展示

### 如果按长期正确方向做

建议的产品/技术方案：

1. source asset 创建时记录真实源媒体信息
2. segment clip 继续保留 `analysis_clip`
3. 发布入库时额外生成 `master_clip`
4. 数据模型中把 `source_clip_path` 拆成：
   - `analysisClipPath`
   - `masterClipPath`
   - `clipGenerationMode`
   - `mediaProfile`
5. 后续：
   - 二创默认优先读 `masterClipPath`
   - 理解 / 预览 / 快速浏览可继续读 `analysisClipPath`

### 关于 master clip 的生成策略

需要产品明确取舍：

#### 方案 A：`stream_copy` 优先

优点：

- 最接近原码流
- 体积与画质最保真

缺点：

- 精确切点可能受 GOP / keyframe 影响
- 起止帧不一定完全精准

#### 方案 B：高保真重编码

优点：

- 切点精准
- 分辨率/帧率可与源保持一致

缺点：

- 仍非原码流
- 体积、时间、CPU 成本更高

我更推荐：

- **分析层**：继续 `reencode_accurate`
- **发布层**：先做 **高保真重编码 master clip**

原因：

- 你的场景更在意“后续二创引用准确”和“素材可稳定复用”
- 比起 `stream_copy` 的切点漂移，高保真重编码更稳
- 等资产库成熟后，再评估是否增加 `stream_copy` 母版备份
